# Оценка помещений по концепции бизнеса

Пользователь описывает концепцию свободным текстом. ИИ формирует один профиль
факторов и приоритетов для всех помещений одного поиска. Код проверяет профиль,
приводит показатели к общей шкале и считает результат. Исполняемых формул от ИИ нет.

```powershell
python run_engine.py --skip-collect --niche "Студия озвучки" --concept "Клиенты приезжают по записи из интернета. Случайный уличный поток не нужен. Важны низкая аренда и удобный путь от метро." --area "40-70" --price 100000
```

В интерактивном режиме концепция вводится шестым вопросом. CLI и Python API
требуют непустое описание бизнеса до сбора данных. Передайте `--concept`
в CLI или `business_concept` в Python API.

```python
report = await aggregator.find_optimal_properties(
    "Кофейня",
    business_concept="Покупатели — сотрудники внутри БЦ. Внешний поток не нужен. Важны внутренняя аудитория и стоимость аренды.",
    max_price_month=150000,
)
```

## Профиль

`report.ranking_profile` содержит факторы, веса, предпочтения, обоснования,
дословные цитаты концепции, предположения и немоделируемые требования.
ИИ выбирает показатели только из доступного реестра измерений. Справочников
«ниша → веса/этажи» для этой формулы нет. ИИ задаёт положительную относительную
важность факторов; код сохраняет их соотношение и нормирует сумму до 1.
Факторы с общим сигналом нельзя включить дважды: например, поток и метро,
аренду в месяц и аренду за м², локальную аудиторию и её же отношение к предложению.

Объявления не передаются в запрос формирования профиля. Профиль кешируется
на час по концепции, названию бизнеса, ограничениям и модели. Ошибки ответа и
сети не кешируются; валидный запрос уточнения кешируется. Общая очередь NVIDIA
учитывает запросы профиля вместе с остальными AI-запросами, с пределом 40 RPM.

До формирования весов отдельная модель разбирает исходные фрагменты концепции:
контекст бизнеса, требования к объекту, снятые требования и предпочтения.
Контекст определяет сценарий, но объявление не должно доказывать рекламу,
запись клиентов или стратегию продаж арендатора. В обязательные проверки
передаются только дословные требования к помещению/допуску/пути.
Один слот на исходный фрагмент предотвращает его автоматическое копирование
во все роли; для смешанного предложения можно выделить точную часть про объект.

Интерпретатор не видит предлагаемых весов или объявлений. Явный главный критерий
превращается в ограничения порядка. Если генератор перепутал важности, код
переставляет уже предложенные величины между группами, сохраняя их набор и
сумму. Фиксированных процентов по нишам нет. Равные важности, не позволяющие
выполнить строгий приоритет, отклоняются. Противоречивый порядок требует уточнения.
Весь разбор вместе с профилем кешируется; все HTTP-попытки входят в общие 40 RPM.

## Расчёт

Полезность известного показателя — от 0 до 100. При предпочтении `higher` она растёт,
при `lower` падает. ИИ не задаёт рублёвые и прочие количественные шкалы:
код использует фиксированные ориентиры клиента или явно заданного Python-профиля.
Максимумы/минимумы текущей выборки больше не определяют шкалу: посторонний лот
не меняет баллы остальных. Для аренды может использоваться явно заданный бюджет.
Бюджет аренды не подставляется как бюджет всех расходов на помещение.
Остальные ориентиры можно передать в `business_data.ranking_scales`; без них
вклад показателя остаётся диапазоном, даже когда его исходное значение известно.
Для индекса потока используется его определённая шкала 0–100.
Для площади `range` означает желаемую полосу из концепции; это мягкое предпочтение,
а не новый жёсткий фильтр. Непроверенные предпочтения обозначаются предположениями.

Границы результата:

```
нижняя = сумма вес × минимальная полезность по диапазону показателя
верхняя = сумма вес × максимальная полезность по диапазону показателя
```

Сортировка использует нижнюю границу. Пропуск не становится фактическим нулём,
а его вес не распределяется на оставшиеся факторы. `score_coverage` показывает
долю веса с заданными значениями/конечными диапазонами. Это не доля измеренных
фактов: диапазон может быть предположением. Пересечение оценок отмечается отдельно.
Это границы по отсутствующим данным, а не статистический доверительный интервал.
Баллы зависят от явно заданных ориентиров; их нельзя трактовать как вероятность успеха.

Проверяются изменения весов ±10% и исходных значений ±20% при фиксированной
референсной шкале. Это сценарии чувствительности, а не доказанные диапазоны ошибок.

## Данные и ограничения

- Экономика аренды не содержит дополнительного бонуса за поток.
- В новой формуле нет бонуса за центр поискового круга или ритм из названия ниши.
- Отношение конкурентов к локальной аудитории — доступный прокси предложения,
  не прогноз рыночной доли. Ноль найденных конкурентов не доказывает свободный рынок.
- Работники соседних офисов не заменяют внутреннюю аудиторию конкретного БЦ.
- Расстояние по прямой не выдаётся за пеший маршрут. Модель поддерживает
  расчёт по предоставленному пешеходному графу, выбор среди альтернатив,
  диапазоны заказов и полной стоимости помещения: [BUSINESS_MODEL.md](BUSINESS_MODEL.md).
  Автоматического получения этих фактов для всех объявлений пока нет.
- Неучтённые требования отражаются в `unmodeled_requirements`; их обработка
  сверяется с реальными фильтрами, условиями допуска и контекстом сценария.
  Значимое требование без обработчика оставляет сравнение неполным.
- Весовые приоритеты ИИ — экспертная гипотеза из описания клиента. Обучения
  на выручке и результатах открывшихся бизнесов пока нет.

Внутренняя аудитория используется только при наличии явно предоставленных
проверенных данных в `raw_json.business_evidence`. Время маршрута поступает
из проверенного внешнего измерения либо рассчитывается по связному графу
между установленными узлами отправления и входа. Пример внутренней аудитории:

```json
{
  "business_evidence": {
    "site_audience_daily": {
      "value": 600,
      "verified": true,
      "source": "Ссылка на реально проверенный документ или замер"
    }
  }
}
```

Число в примере условное. ИИ эти значения не заполняет. Ответственность за
достоверность внешнего подтверждения лежит на поставщике этих данных.
Аналогично поддерживаются `walk_time_minutes` и `delivery_time_minutes`.

## Проверки

```powershell
python -m unittest discover -s tests -v
python audit/scripts/check_ranking_stability.py
```

Текущий аудит проверяет неизменность баллов при добавлении постороннего лота,

вызывает ИИ для одной концепции. Данные и ориентиры синтетические; это проверка

Прежние отчёты в `audit/concept_ranking_2026-11-04/` относятся к первой версии.

## Автоматическая проверка условий помещения

После рейтинга показанные кандидаты проходят отдельный этап подтверждения.
`candidate.confirmation` содержит статус, причины, проверенные источники,
ссылки на факты и независимую проверку достаточности доказательств:

- `requires_confirmation` — «Требует подтверждения»; неизвестное не становится разрешением.
- `source_conditions_checked` — опубликованные условия проверены для концепции клиента.
- `not_suitable` — доказано нарушение обязательного условия; кандидат убирается из рекомендаций.

Проверяются актуальность публикации, назначение, доступ и обязательные условия
концепции, изменения площади/цены/этажа и недостающие расходы. Проверка публикации
не означает ответ собственника или осмотр. Числовой рейтинг от этого не меняется.
Условия соседних лотов не переносятся на выбранное помещение.

Поддержан отдельный адаптер публичного каталога Mega Realty: сайт издателя
обнаруживается по точному названию организации, затем проверяются номер лота,
адрес и площадь. Для площадок есть консервативное чтение JSON-LD с точной
привязкой к объявлению. Другие структуры, блокировка и неоднозначная привязка
дают `requires_confirmation`. Поддержка всех форматов сайтов не заявляется.
Успешные снимки источников переиспользуются до 5 минут с исходным временем
получения; ошибки не кэшируются как успешные проверки.
Перед обращением к ИИ почти истёкший снимок обновляется; свежесть повторно
проверяется при принятии решения. Актуальные числовые условия отдельно
сопоставляются с эффективными фильтрами клиента: допуск сравнения старой и
новой цены не разрешает превышать бюджет. Недостаточные или неконечные
числовые данные не дают подтверждения. Независимая модель проверяет каждое
условие отдельно; сбой одного пункта сохраняет подтверждённые факты остальных.
`confirmation_timeout_s` ограничивает этап (по умолчанию 45 секунд), запросы ИИ
проходят через общий лимитер NVIDIA 40 RPM. По истечении бюджета остаётся
«Требует подтверждения».

Независимый проверяющий назначений задаётся `NVIDIA_PROPERTY_PROOF_MODEL`
(по умолчанию `nvidia/nemotron-3.5-super-vl-120b-a12b`). Она отличается от
основной модели подтверждения, задаваемой `NVIDIA_PROPERTY_ASSESSMENT_MODEL`
(по умолчанию `nvidia/nemotron-3.5-lightning-30b-a3b`). Та же Super используется как
независимый проверяющий классификации организаций; явные настройки моделей
имеют приоритет. Скрытого переключения при ошибке нет. Для доказательства
Nemotron выделено не менее 800 токенов с выключенным thinking; явная
конфигурация прежней модели Mistral сохраняет бюджет рассуждений.
Принимаются только ответы, завершённые `finish_reason=stop`.
Длинное, но полное пояснение до 2000 символов сокращается для показа до 220,
исходный текст сохраняется в `reason_full`. Это не изменяет вывод, ссылки
на факты и требования к JSON. Пустой, повреждённый или незавершённый ответ
по-прежнему не даёт подтверждения.

На соединение независимого проверяющего отводится до 5 секунд внутри общего
бюджета. Для быстрой основной и независимой проверок помещения каждая
HTTP-попытка ограничена 12 секундами; один повтор допустим при временном
сетевом отказе или HTTP 502–504 внутри прежнего общего дедлайна. Он также
проходит общий лимитер 40 RPM. Неверный JSON и незавершённый ответ не
повторяются этим транспортом. Для явной медленной конфигурации Mistral
прежнее правило сохраняется: повтор только ошибки соединения/прокси.
`error_phase` и `source_errors` различают сетевой сбой, HTTP-статус, очередь
лимитера, дедлайн и ошибку привязки/формата источника. Адреса прокси и ключи
в эти диагностические поля не записываются.

`confirmation.processing_status` отдельно показывает, завершился ли анализ
(`complete`/`partial`/`unavailable`), а `completed_conditions` — сколько пунктов
получило законченный ответ. `requires_confirmation` может остаться и при
полностью завершённом анализе: факты не доказывают разрешённость использования
или свободный доступ. Причины различаются через `reason_type`.

Для неизвестных организаций автоматически проверяются публичные полные
карточки по точному ID (до 8 карточек за запрос, две одновременно). Изменённые
факты повторно классифицируются с независимой проверкой, без новых правил по
нишам. География и идентификатор проверяются; противоречия не стираются.
Сохраняются признаки без подписанного имени и значения перечислений.
`organization_detail_completion` показывает добранные и отложенные карточки.

Для датированного пассажиропотока станций с совпадающим названием на разных
линиях сохраняется минимум/максимум одной линии. Потоки линий не суммируются,
точечное значение не выдумывается. Диапазон участвует в аудитории рейтинга;
пешеходный поток у входа остаётся неизвестным без соответствующего источника.

`card.fns_diagnostics` различает неустановленное юрлицо, отсутствие отчётности
по установленной компании и доступную отчётность. Данные компании не
превращаются в выручку конкретной точки. Публичные сайты разных компаний
проверяются независимо (до 4 одновременно), в пределах 12 секунд на сайтный
поиск. Рекламные метки ссылок удаляются из дублей, функциональные параметры
магазина и подписанные ссылки сохраняются.

Для короткого списка (число допущенных к анализу помещений не больше числа
показываемых) проверка опубликованных условий начинается параллельно с
анализом окружения. При формировании отчёта её результат переиспользуется
только при неизменных фактах помещения и расчёте расходов; свежесть источников
проверяется снова. Большие списки не отправляются в ИИ заранее.
`confirmation_execution` показывает число ранних проверок и переиспользований.
`stage_timings_ms.confirmation` в таком режиме отражает оставшееся ожидание
после рейтинга, а не полное время работы ИИ; общее время поиска включает всё.

Завершённые независимые доказательства `supported`/`unsupported` могут
переиспользоваться до 240 секунд и не дольше срока актуальности исходного
снимка. Ключ включает концепцию, все факты и противоречия, ссылки на источник,
проверяемый вывод, модель и версию контракта. Неизвестные ответы, сетевые сбои
и таймауты не сохраняются. Параллельные одинаковые запросы делят одну работу;
отмена одного клиента не отменяет остальных. Эта оптимизация не меняет баллы
и не подтверждает неизвестные условия.

`report.next_actions` содержит действие «Найти ещё варианты» и параметры
продолжения. Выполнение через API:

```python
next_report = await aggregator.find_more_options(report)
# Либо напрямую:
next_report = await recommender.find_more_options(report)
```

Сохраняются концепция, география, бюджет, площадь и остальные исходные условия;
уже показанные ключи объявлений исключаются. Автоматического расширения радиуса
или бюджета нет. После сериализации отчёта исходные `business_data`, если они
использовались, нужно передать снова: они не дублируются в JSON действия.
CLI выводит готовую команду продолжения с повторяемым `--exclude-property`.
Переписка, бронь и другие действия с третьими лицами этим этапом не выполняются.

Клиентский сбор теперь использует `aggregator.collect_for_search(request)`:
глубина увеличивается при недостаточном числе свежих числовых совпадений,
без расширения территории или бюджета. По умолчанию начальная глубина 30,
рост в четыре раза, предел первого сбора 600 объявлений на площадку.
Размер рабочей выборки — операционный параметр, а не критерий пригодности бизнеса.
`find_optimal_properties(..., refresh_inventory=True)` включает этот сбор через API;
CLI вызывает его по умолчанию, кроме явно указанного `--skip-collect`.
`report.inventory_collection` хранит проходы, ограничения, причину остановки
и предупреждение о неполном охвате рынка. Если собранные варианты закончились,
`aggregator.find_more_options` догружает следующий объём с теми же фильтрами
и исключениями. Рост ограничен общим пределом 2400 на площадку;
после его достижения отсутствие совпадений относится только к просмотренной выборке.
Прямой `recommender.find_more_options` работает с уже собранной базой.

### Выбор клиента: продолжить с неподтверждёнными условиями

По умолчанию варианты `needs_verification` не допускаются к рейтингу.
Если такие варианты есть, `report.next_actions` дополнительно предлагает
`continue_unverified` — «Продолжить предварительный анализ». Выполнение этого
действия требует выбора клиента; система не включает его автоматически.

```python
# Обработчик явного выбора клиента:
report = await aggregator.continue_unverified_analysis(report)

# Либо клиент сразу выбрал соответствующую опцию:
report = await aggregator.find_optimal_properties(
    target_business=business,
    business_concept=concept,
    include_unverified=True,
)
```

CLI: `--include-unverified`. В интерактивном режиме после строгого поиска
предлагается продолжение с ответом «нет» по умолчанию. Команды продолжения
сохраняют фактически введённые клиентом условия и выбранную опцию, а не только
исходные аргументы запуска.

Опция добавляет к анализу окружения и обычному расчёту пригодности только
неопределённые варианты. Доказанные нарушения обязательных требований,
числовые фильтры и исключения клиента не обходятся. Неподтверждённые параметры
не заменяются нулями или положительными ответами; веса профиля не меняются.
Известное нарушение при последующей проверке источника исключает помещение.

`report.include_unverified` хранит выбранный режим,
`unverified_evaluated_count` — число фактически оценённых вариантов с
неподтверждённым допуском. Их `floor_assessment.status` сохраняется, а
`confirmation.status` остаётся `requires_confirmation` с исходными причинами.
Даже положительный ответ последующей проверки источника не стирает прежний
неподтверждённый допуск без его повторной оценки. `comparison_complete=False`;
первый в рейтинге — предварительный вариант для проверки, а не подтверждённо
лучшее помещение. Пересекающиеся диапазоны и чувствительность показываются
по обычным правилам модели. Оценённые варианты не дублируются в списке ещё
неоценённых `floor_verification_candidates`.

Действия API сохраняют координаты, радиус, концепцию, цены, площадь,
`business_data` и исключения. Для `continue_unverified` исключаются только
исходно запрещённые клиентом варианты, а не ожидающие проверки помещения,
ради которых он выбрал продолжение. `find_more` затем исключает показанные
варианты и сохраняет `include_unverified=True`. После сериализации отчёта
`business_data`, если они использовались, передаются явно повторно.

Нативный контракт проверки размещения v5 генерирует только `reason` и
`checks`. `missing_facts` вычисляется кодом из проверок с результатом unknown,
что устраняет противоречивое повторное описание одного результата моделью.
Проверка обязательных условий и независимых доказательств сохраняется.
Неизвестный номер этажа больше не блокирует контекстную оценку сам по себе:
без явного `allowed_floors` проверяются требования клиента, допуск и путь до
помещения. Неподтверждённое условие остаётся unknown. При явном списке этажей
отсутствующий этаж по-прежнему требует уточнения; противоречия источника
сохраняют отдельную остановку. Отсутствующий номер отмечается предупреждением
и не подставляется моделью. Положительный вывод требует прежних независимых
доказательств доступа, а не одного прохождения предварительной проверки.
Адаптер ЦИАН читает JSON-состояние именно `frontend-offer-card/defaultState/offerData/offer`;
объекты рекомендаций не используются. Привязка проверяет ID в URL и состоянии,
адрес, площадь, тип сделки и текущую месячную цену. Поисковый параметр URL
не меняет идентичность лота; JavaScript страницы не исполняется.

### Требования к помещению по описанию клиента

Из свободного запроса извлекаются отдельные физические условия и пожелания.
Этот этап видит только запрос клиента. При проверке объявления состав условий
фиксирован. Каждая строка сохраняет цитату, обязательность, результат и
ссылки на подтверждающие сведения. Доказанное несоответствие обязательному
условию исключает вариант. Неясное обязательное условие оставляет сравнение
предварительным. Пожелания видны в отчёте и сами по себе не исключают лот.
Независимая модель проверяет роль извлечённых цитат перед использованием
условий. Разрешения и снятые ограничения сохраняют свой смысл. При недоступном
источнике успешно извлечённые условия остаются в отчёте с открытым статусом.

Для открытых условий короткого списка визуальная модель получает до трёх
фотографий, привязанных к карточке лота. Она оценивает видимые признаки с
учётом текста объявления. Результат «Видно на фото объявления» отличается
от текстового подтверждения. При неполном ракурсе, неясной принадлежности
снимка или недоступности API условие остаётся открытым. Мощность, разрешения,
работоспособность и точные размеры требуют подходящего источника.

Обустройство и смету определяет арендатор. Затраты на подготовку входят
в экономику только при наличии предоставленных клиентом данных.

### Пешеходные препятствия и транспортная аудитория

Автоматический граф OSM строится по общим идентификаторам узлов. Близость
точек не создаёт переход через дорогу, пути, воду или ограждение. Геометрическая
проверка дополнительно исключает пересечения с нанесёнными препятствиями,
если нет подтверждённого перехода, разрешённого прохода или разноуровневого
моста/тоннеля. Совпадение координат внутри моста не соединяет его с землёй.
Проезды, переулки, дорожки и лестницы участвуют при наличии связей и допуска
пешеходов; осевая линия крупной автодороги не заменяет тротуар.

Условия `opening_hours`, `foot:conditional`, `access:conditional` и
`locked:conditional` пока не разрешаются для конкретного момента времени.
Такие связи не считаются подтверждённо доступными. Текущие перекрытия и
не нанесённые на карту заборы автоматически не устанавливаются.
Отсутствующий путь в неполном графе означает unknown, а не доказанный запрет.

Время складывается из длины пути при явно указанной скорости и диапазонов
ожидания. Для светофоров и железнодорожных переходов неизвестное ожидание
не заменяется фиксированным числом: нижняя граница ожидания равна нулю,
верхняя отсутствует. Альтернативный путь с конечной оценкой даёт конечную
верхнюю границу. Это расчёт по карте, а не измеренное время прогулки.
`minutes` заполнено только при совпадающих границах; иначе используются
`minutes_lower` и `minutes_upper`. В изохроне `nodes` показывает возможную
достижимость по нижнему времени, `guaranteed_nodes` — достижимость в рамках
данного графа и предположений по верхнему времени. Это не гарантия условий
на местности. Все источники, даты и принятые ограничения сохраняются.

В рабочем сборе `FootTrafficReport.transport_routing_required=True`.
Перед рейтингом `condition_transport_on_routes` связывает каждый источник
пассажиропотока с установленными выходами/остановками и входом здания.
Станция связывается по имени или отношению OSM `stop_area`; остановка — по
однозначному совпадению имени и координат существующего узла либо явному ID.
Ближайшая станция с другим именем не получает чужой пассажиропоток.
Вклад каждой станции определяется её маршрутом и собственным сценарным
диапазоном экспозиции. Доли не перераспределяются между станциями при смене
их порядка: удлинение одного маршрута не может повысить аудиторию за счёт
повышения коэффициента другой станции. Несколько выходов одной станции
не умножают её пассажиропоток.

Неизвестная привязка, неоднозначный вход или путь с неограниченным сверху
ожиданием не дают положительного нижнего вклада транспортной аудитории.
Возможный верхний вклад сохраняется; это не утверждение об отсутствии спроса.
Геодезический транспортный прокси без обработки маршрутов не принимается
в рейтинг рабочего сбора. Уже учтённая в транспортном компоненте пешая
доступность не применяется к нему повторно. Доступность остальных компонентов
аудитории остаётся отдельным фактором с собственными неизвестными данными.

Датированный пассажиропоток станции — исходный факт; доли экспозиции,
затухание по времени и скорость ходьбы — явные некалиброванные предположения.
Результат не является измеренной проходимостью у входа или числом клиентов.
Нанесённый вход здания также не доказывает доступ к конкретному помещению.
Автоматический локальный граф всегда помечается неполным; путь, выходящий
за загруженную область, нельзя объявлять невозможным. Проверки реализации:
[audit/route_barriers/REPORT.md](../audit/route_barriers/REPORT.md).

## Проверка диагностической согласованности

Рейтинг проверяется на соблюдение условий клиента, сумму вкладов, независимость
от порядка записей, монотонность исходных факторов и устойчивость к предположениям.
В повторном расчёте 21 сохранённого отчёта — 30 оценок 17 разных объявлений —
числовые ограничения и известные этажи соблюдены; противоречащих требованиям
вариантов среди ранжированных не найдено. По 112 вариациям опорных уровней и
коэффициентов в двух конфигурациях одного отчёта менялся лидер; исходный отчёт
уже имел статус `needs_data`, а не подтверждённого преимущества.

Устойчивость отдельно проверена на 500 контрольных парах и 7000 изменениях
коэффициентов ×0,5/×2. В 97 конфигурациях менялась первая позиция; все они
попадали под действующие признаки неопределённости исходных данных или весов.
Эти множители задают область стресс-проверки, а не доверительные границы рынка.

Плюс или минус критерия теперь определяется всем интервалом его полезности.
Если интервал пересекает уровень 50/100, он выводится как неопределённость.
Сведения о пропусках и модельных допущениях не перечисляются как установленные
недостатки помещения. Описание использует диапазон исходного значения и вклада,
а не выдаёт середину диапазона за наблюдение.

Повторяемый аудит без сети, ИИ и изменения рабочей базы:
`python audit/scripts/check_diagnostic_consistency.py --output audit/diagnostic_ranking/verified.json`.
Подробности и границы проверки: [отчёт](../audit/reports/diagnostic_consistency.md).

### Автоматическая чувствительность сценарных коэффициентов

После проверки объявлений, обновления цен и группировки дублей обычный подбор
дополнительно пересчитывает индекс окружения, поочерёдно меняя незаданные
клиентом опорные уровни, `competition_scale`, `outside_pressure` и активное
опорное время доступности ×0,5/×2. Приоритеты концепции, внешние веса и
предоставленные клиентом или контрольным набором параметры остаются прежними.
Происхождение предоставленных параметров сохраняется отдельно для каждого поля.

`model_sensitivity` содержит проверенные сценарии, конкретные причины смены
лидера, значения коэффициентов и ID альтернатив. `model_sensitive_challenger_ids`
добавляются к сопоставимым вариантам вместе с альтернативами по исходным данным
и весам. Если сравнение завершено и нет блокирующих пропусков, такой результат имеет
статус `comparable`. Незавершённая проверка даёт `needs_data`, а её ошибка
сохраняется как `model_sensitivity_unavailable`. Подтверждение условий самого
объявления остаётся отдельной проверкой.

Это проверка по одному коэффициенту за раз в явно указанном диапазоне;
совместное изменение всех предположений и калибровка по исходам бизнеса сюда
не входят. Проверка выполняется локально по уже собранным данным.
Результаты: [автоматическая проверка допущений](../audit/reports/model_sensitivity.md).

### Практический результат и полнота сведений

Группа стоимости допускает `rent_month` и `premises_cost_month`: выбирается
один показатель по смыслу запроса. Одна аренда использует бюджет аренды как
явный ориентир. Полные расходы требуют отдельного клиентского ориентира;
его отсутствие запрашивается до дорогих проверок, через `provide_references`.
Стартовая ставка торгов — нижняя граница, окончательная аренда неизвестна.
При жёстком бюджете такой вариант ожидает подтверждения и доступен для
предварительного сравнения только по выбранной клиентом опции.

`comparison_complete` описывает завершение сравнения отобранных объявлений,
`data_complete` — полноту использованных данных, `confirmation_status` —
проверку опубликованных условий. Эти признаки не заменяют друг друга.
Неизвестные данные остаются в числовых диапазонах. Сохраняющееся преимущество
можно обозначить при неполных сведениях; при пересечении диапазонов выводятся
сопоставимые варианты. Непроверенные обязательные условия сохраняют свою пометку.
Общий охват рынка отдельно хранится в `inventory_collection`.

Отложенные варианты с неизвестным допуском дополнительно получают безопасную
условную верхнюю оценку из известных цены/площади и полного диапазона 0–100
для остальных критериев. Если даже эта граница не достигает нижней оценки
известного лидера при изменении исходных значений ±20% и весов ±10%, такой
вариант не препятствует первому выбору. Доказательство хранится в
`deferred_candidate_bounds`. Неизвестный допуск остаётся неизвестным; вариант
не объявляется подходящим и не добавляется в обычный рейтинг. Для актуальных
неучтённых требований такой отсев не выполняется. Границы пересчитываются
после уточнения опубликованной цены и смены лидера.

`recommendation` содержит следующий шаг, ID первого варианта для проверки
(при наличии оснований), числовые основания в `basis` и сгруппированные
проверки `checks`. При одинаковой нижней оценке приоритет не создаётся
технической сортировкой по источнику или ID. При неучтённом требовании
запрашивается уточнение его обработки. Ширина в `uncertainty_points` относится
ко всему критерию, а не оценивает отдельный факт или вероятность успеха.

Числовая фраза считается учтённой фильтрами только при совпадающих единицах,
обеспечивающих её ограничениях и выполнении этих условий у сравниваемых
объявлений. Дополнительные свойства внутри такой фразы не отбрасываются.
Самостоятельно выполняемая клиентом работа отмечается `client_managed`.
Сведения о его бизнесе — `scenario_context`; распознанное условие помещения
с недостающим доказательством — `verification_pending`. Последнее означает
необходимость проверки факта, а не повторного объяснения концепции.

Цитаты условий выбираются из исходных текстовых фрагментов в схеме, без
переписывания слов. Неиспользуемая аннотация отказа при активном источнике
аудитории нормализуется в `null` с записью в метаданных; применимость и вес
источника не меняются. Для реально исключаемого источника сохраняется строгая
проверка основания отказа.
